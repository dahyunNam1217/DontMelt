# 4단계 — 유물·상호작용

## 22. 유물 시스템 상태와 소유권 설계

유물의 실제 상태, 운반자, 상자 등록 수가 서로 다른 객체에서 경쟁하지 않도록 원본을 정했다. 클라이언트는 상호작용 요청만 보내고 결과는 서버에서 확정한다.

**구현 및 판단**

- RelicActor는 개별 유물 상태 표현
- RelicManager는 유물 수명·이전과 드롭/등록 관리
- 상자와 플레이어 UI는 원본을 읽어 표시

**결과**

유물 하나가 바닥·운반·상자에 동시에 존재하는 상황을 금지하도록 상태 전이를 정리했다.

## 23. 매치 시작 유물 배치 및 스폰 지점

매치 시작 인원을 기준으로 유물 수량을 결정하고 지정 지점에 배치하는 구조를 구성했다. BaseZone, RelicSpawnPoint, RelicChest는 이름은 비슷하지만 전혀 다른 역할이다.

**구현 및 판단**

- BaseZone은 플레이어 진영·Respawn 기준
- RelicSpawnPoint는 초기 유물 배치 지점
- RelicChest는 등록·탈취 상호작용 대상

**결과**

코드는 지점의 개수와 용도를 검증하고, 실제 위치와 Collision은 레벨 배치에서 맞춘다. 공용 유물 지점이 정확히 1개가 아니면 유물 초기화가 실패하도록 했다.

## 24. 공용 유물 Pickup 상호작용

바닥 유물을 F 길게 눌러 획득하는 흐름을 연결했다. 서버가 거리와 유물의 현재 상태를 검증한 뒤 Carried 상태로 이동시킨다.

**구현 및 판단**

- Hold 시작·취소·완료를 명시적으로 구분
- 플레이어당 동시 운반 수 제한
- 다른 플레이어가 먼저 획득하면 기존 요청은 실패 처리

**결과**

클라이언트 진행 바 완료만으로 유물 소유가 바뀌지 않도록 완료 시 재검증을 유지했다.

## 25. 상자 열기와 Input Mapping Context 전환

F 한 번으로 Chest Inspect 화면을 열고, 열린 동안 `IMC_Interaction`으로 전환하는 조작을 확정했다. Space를 누르는 동안 등록·탈취가 진행되며 F는 상자를 닫는다.

**구현 및 판단**

- 일반 이동 입력과 상자 전용 입력을 분리
- Space Hold 해제 시 시도 취소
- Chest 닫기 후 Gameplay Context 복원

**결과**

상자를 닫았는데 이동키가 남거나 Space가 점프와 등록을 동시에 실행하는지 확인하도록 했다.

## 26. Interaction Session과 Request ID

같은 대상에 대한 동시 요청과 늦게 도착한 완료 메시지를 구분하기 위해 서버 Session과 Request ID를 사용했다.

**구현 및 판단**

- 요청마다 시작·진행·중단 구간 식별
- Session 소유자와 대상 유물/상자를 일관되게 관리
- 새 요청이 과거 요청의 결과를 물려받지 않도록 경계 확인

**결과**

네트워크 지연이 있어도 현재 유효한 요청만 Commit할 수 있도록 설계했다.

## 27. Reservation과 완료 직전 재검증

유물 하나를 두 사람이 동시에 줍거나 등록하지 못하도록 Reservation 정책을 설정했다. Hold 도중 시작 조건이 맞았더라도 Commit 시 다시 검증한다.

**구현 및 판단**

- 거리·생존·상호작용 가능 여부·점유 여부 점검
- 취소/사망/Disconnect 시 Reservation 해제
- 유물 상태 변경은 서버 원자적 Commit에서 확정

**결과**

Begin 조건과 Complete 조건을 같은 것으로 취급하지 않는 구조를 채택했다.

## 28. 유물 Q 드롭 및 재획득 제약

운반 중 Q로 드롭하는 경로를 정리하고 자기 상자 근처에서 드롭하는 악용 가능성을 점검했다. 같은 플레이어가 방금 떨어뜨린 유물을 즉시 줍는 경우도 제한했다.

**구현 및 판단**

- Carried→World 상태 변경을 서버에서 수행
- 드롭 위치와 상자 근접 조건 검증
- 동일 플레이어 재획득 제한 시간을 서버가 관리

**결과**

수동 드롭과 사망·접속 종료 시 자동 드롭은 발생 원인이 다르지만 동일 유물 상태 규칙을 통과시킨다.

## 29. 유물 등록과 보호 시간

유물을 들고 자기 상자를 열어 Space를 유지하면 서버가 등록을 확정한다. 등록된 유물에는 곧바로 재탈취하지 못하는 보호 구간을 둔다.

**구현 및 판단**

- 운반 유물과 상자 BaseSlot 일치 검증
- 등록 완료와 단순 Progress 완료 구분
- 보호 타이머 종료 이후 탈취 가능 상태 전환

**결과**

등록 Count는 UI에서 직접 더하지 않고 서버의 상자·관리자 데이터를 읽는다.

## 30. 상대 상자 탈취와 알림 정책

상대 상자에서도 동일한 Session 경로를 사용하되, 등록과 탈취를 구분했다. 도난 알림은 관련 당사자에게 필요한 정보만 전달하도록 검토했다.

**구현 및 판단**

- 상대 BaseSlot·등록 상태·보호 기간 검사
- 탈취 시 운반 가능 여부와 상자 Count 재확인
- 진행 중 다른 시스템이 상자 내용을 변경한 경우 취소 처리

**결과**

상자 Count를 읽는 권한과 상대방에게 직접 알려주는 정보 범위를 분리했다.

## 31. 유물 상태 복구와 Disconnect 처리

유물 운반자의 사망·퇴장·월드 분실 가능성을 별도의 복구 경로로 관리했다. 경기가 끝난 뒤에는 이전 진행 중인 상호작용을 재개하지 않도록 했다.

**구현 및 판단**

- Death/Disconnect 시 유물 안전한 위치로 드롭 또는 회수
- RelicManager 기준 분실 확인과 Recovery
- Match Finished 이후 Gameplay Commit 차단

**결과**

바닥이 없는 위치의 유물은 1초 주기 검사로 지정된 복구 지점에 옮긴다. 임의 좌표에 새로 만들지 않는다.

## 32. 유물 승리 판정과 동률 처리

승패를 유물을 실제로 상자에 등록한 최종 수량으로 판단하도록 구성했다. 게임 중 운반 중인 유물 수와 등록 수를 혼동하지 않도록 별도 통계를 유지한다.

**구현 및 판단**

- GameMode만 최종 승패를 확정
- GameState는 공개용 결과를 복제
- 운반 중인 유물은 등록 수에 포함하지 않음

**결과**

결과표의 표시 열은 10단계에서 등록 수(순위 기준)와 누적 획득 수(표시용)로 나눴다.

## 33. 유물 HUD 및 상호작용 안내 분리

운반 중인 유물과 상호작용 안내를 구분했다. 코드가 보유하지 않은 원본 정보를 위젯이 자체 계산하지 않도록 경계를 잡았다.

**구현 및 판단**

- RelicHUD는 운반·Q 드롭 안내 중심
- InteractionPrompt는 F/Space 진행·대상 안내 중심
- 상자 창에는 등록·탈취 상태 표시

**결과**

10단계에서 ChestCount/Action 등 중복 텍스트를 삭제하는 방향으로 UI를 다시 정리했다.

## 34. 4단계 최종 구조·동시성 점검

Pickup, Drop, Deposit, Steal, Death, Disconnect, Recovery가 같은 유물 상태 머신을 이용하는지 검토했다. Tick보다 요청·Timer·Delegate로 상태를 갱신하도록 정리했다.

**구현 및 판단**

- 중복 수집과 두 개의 상자에 중복 등록되는 경로 확인
- 완료 전 대상 파괴·거리 이탈·매치 종료 확인
- Stage 5 사망 처리에서 Drop 경로를 재사용

**결과**

유물 기능 자체의 구조는 동결하고 전투 단계에서 사망 연동을 추가하는 기준으로 남겼다.

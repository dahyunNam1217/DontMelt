# 패키징 전 전체 소스 정적 검수와 묶음 단위 수정 적용

멀티플레이 패키징 테스트를 앞두고, **실행 전에 찾을 수 있는 문제를 최대한 찾기 위해** 전체 소스를 두 차례 검수했다. 이 문서는 무엇을 찾았는지보다 **어떻게 찾고, 어떻게 걸러 내고, 어떻게 안전하게 반영했는지**를 정리한 것이다.

| 회차 | 범위 | 결과 |
|---|---|---|
| 1차 | C++ 소스 약 170개, Config 4개, 단계별 설계서(2~11.5단계)와 기획서 | 확정 결함 5 · 잠재 결함 9 · 설계 불일치 6 · 개선 8 · 추가 테스트 6 → 수정 파일 26개 |
| 2차 | 책임 분리 리팩토링 이후 소스 전체 | 확정 결함 3건을 포함한 수정 14건 → 5개 묶음으로 나눠 적용, 코드 묶음 4개 모두 첫 빌드 성공 |

## 1. 검수 원칙

| 원칙 | 내용 |
|---|---|
| 코드 기준 | 기억이나 문서가 아니라 **최신 소스의 실제 코드**로 판단한다 |
| 사실과 추정 분리 | 코드 경로로 확정되는 것과, 타이밍·에셋·환경에 따라 달라지는 것을 나눈다 |
| 최소 수정 | 문제가 없는 코드는 고치지 않고, 대규모 재작성을 하지 않는다 |
| 근거 명시 | 모든 항목에 경로·클래스·함수·발생 조건·영향·검증 방법을 붙인다 |

## 2. 분류 체계

| 분류 | 의미 |
|---|---|
| 확정 결함 | 코드 경로상 반드시 잘못 동작한다 |
| 잠재 결함 | 특정 조건(타이밍, 맵 배치, 실패 상황)에서 잘못 동작한다 |
| 설계 불일치 | 코드와 기획·설계서가 다르다 |
| 개선 권장 | 동작은 하지만 품질·유지보수·배포 측면에서 개선이 필요하다 |
| 추가 테스트 필요 | RPC 순서, 엔진 설정 상속처럼 정적 분석으로 판정할 수 없다 |
| 검증 불가 | `.uasset`, 맵, Steam 환경처럼 소스 밖에 있다 |

심각도는 P0(진행 불가)부터 P4(정리)까지 매겼다.

## 3. 찾는 방법

### 게임 흐름 순서로 읽기

파일 순서가 아니라 **플레이 흐름 순서**로 읽었다.

```text
타이틀 → 세션 생성/참가 → 로비 → ServerTravel → 매치 시작
→ 이동·전투·상호작용·유물·스킬·퀘스트·이벤트 → 사망·관전·리스폰
→ 정규/연장 종료 → 결과 → 로비 복귀 / 재경기 → 종료·네트워크 실패 복구
```

각 단계에서 다섯 가지를 확인했다.

| 관점 | 질문 |
|---|---|
| 권한 | 판정을 서버만 하는가 |
| 복제 | 복제 조건과 정보 은닉이 맞는가 |
| 호출 경로 | 정의된 RPC와 Delegate가 실제로 호출되는가 |
| 실패 분기 | 모든 실패 경로에 복구나 해제가 있는가 |
| 반복 작업 | Tick·타이머·Delegate의 등록과 해제가 짝을 이루는가 |

### 기계적 검색으로 보조

| 검색 | 찾은 것 |
|---|---|
| **호출 0건 검색** (선언·정의만 있고 호출 없는 함수) | [결과 ACK 호출 누락](../Debugging/Network/07_MatchResult_Travel_Race.md), [감정표현 진입점 누락](../Debugging/Gameplay/11_Quest_Emote_Input.md) |
| `Tick`, `NativeTick`, `bCanEverTick`, `GetAllActorsOfClass` | [성능 비용 판단](../Performance/02_Cost_Design.md)의 근거 |
| 위젯마다 `Add`/`Remove`, `SetTimer`/`ClearTimer` 개수 비교 | 해제 누락 후보 |
| UTF-8 디코딩 실패 파일 | [CP949 파일 2개](../Refactoring/04_Code_Hygiene.md) |

### 설계 문서와 대조

코드만 보면 "없는 기능"은 결함으로 보이지 않는다. 기획서와 단계별 설계서의 규칙을 코드와 하나씩 대조해 찾은 문제가 있다.

- [정규 시간 단독 1위 승리 누락](../Debugging/Gameplay/10_RegularTime_Winner.md)
- [결과표 데이터 의미 불일치](../Refactoring/03_MatchResult_Data.md)
- 생존·사망 상태별 근접 음성 청취 정책 미구현 → [음성 채팅](../Technical/14_Voice_Chat.md)에 구현

### 2차 검수: 증상에서 역추적

2차 검수는 기능 순서가 아니라 개발 내내 겪은 증상, **"Steam 세션 생성이 안 되고 클라이언트가 로비에 못 들어간다"** 에서 출발했다. 그 증상이 나올 수 있는 모든 경로를 먼저 펼쳤다.

```text
"세션 생성 안 됨 / 로비 진입 불가"
  ├ 세션 생성 자체가 거절됨       → 남은 세션
  ├ 세션 작업이 영구 Busy         → 타임아웃 없음
  ├ 로비가 검색에 안 보임         → 서버 필터 없음
  ├ 접속 주소로 이동 실패         → NetDriver 설정
  ├ 이동 중 끊김 오탐             → 이동 상태 미확인
  └ 로비에 들어갔지만 목록이 빔   → 바인딩 재시도 소진
```

로비 이후는 **"멈추는 상태"** 와 **"사라지는 것"** 을 기준으로 봤다.

| 기준 | 찾은 것 |
|---|---|
| 끝나지 않는 대기 상태 | [경기 Waiting 기한 없음](../Debugging/Network/10_Match_Waiting_Timeout.md) |
| 다시 손댈 수 없게 되는 오브젝트 | [벽 속 드롭 유물](../Debugging/Gameplay/05_Relic_Drop_Wall.md) |
| 관찰자마다 다르게 보이는 상태 | [투명화 Relevancy](../Debugging/Gameplay/01_Invisibility_Relevancy.md) |
| 정보가 새는 배치 | [NPC 분포 편향](../Debugging/Gameplay/12_NPC_Spawn_Shuffle.md) |
| 네트워크 경계 오차 | [쿨다운 서버 시간 추정](../Debugging/Gameplay/06_RemoteCooldown_Tolerance.md) |

## 4. 걸러 내는 방법

### 교차 검증

같은 소스에 대한 별도 검수 의견을 받아 항목별로 비교했다. 두 결과를 합치지 않고, **각 주장을 코드와 설계서에서 다시 확인한 뒤** 채택 여부를 정했다.

| 결과 | 항목 | 판단 근거 |
|---|---|---|
| 채택 | 감정표현 퀘스트 경로 누락 | 코드 확인. 추가로 "Server RPC가 BlueprintCallable이 아니다"를 찾아 "BP 경로는 검증 불가"를 **확정 결함으로 격상** |
| 심각도 상향 | 근접 음성 미구현 P3 → P1 | 기획서에서 핵심 규칙임을 확인 |
| 결론은 같고 방법은 기각 | 결과 ACK를 위젯에서 송신 | UI 표시 조건에 따라 ACK가 빠질 수 있음. 데이터 계층에서 송신 |
| 보정 후 채택 | 공동 순위 코드에서 승자 정보 제거 | "승리 판정은 바꾸지 않는다"는 설계 원칙에 따라 승자를 동률 시 표시 순서로 유지 |
| 유지 | 연장전 Deposit Drop, LOS, 리스폰 고립, 로비 잠금, NetDriver, 엔진 PTT 충돌 | 별도 의견에 없던 항목. 근거를 다시 확인하고 유지 |
| 새로 발견 | 정규 시간 승리 누락의 근거 | 교차 검증 중 설계서를 다시 읽다가 확인, P3 → P2 |

### 판단을 바꾼 지점

검수 결과를 그대로 다 고치지 않았다. 근거, 기획 의도, 회귀 위험으로 한 번 더 걸렀다.

| 항목 | 처음 판단 | 최종 판단 | 근거 |
|---|---|---|---|
| GameState 상한 `5` | 데이터가 늘면 연출이 사라지는 결함 | 값은 맞음, 의미만 상수화 | 유물 생성 코드가 진영 수 + 1로 고정 |
| 퀘스트 실패자가 남으면 퀘스트 지속 | 이후 이벤트 차단 결함 | 의도한 동작, 제외 | 기획 확인 |
| 입력 반전 이벤트 중 리스폰 | 수정 대상 | 제외 | 이벤트 시작 조건이 "전원 생존"이고 리스폰이 30초라 실제로 발생하지 않음 |
| 친구 목록 참가 끄기 | 수정 대상 | 보류 | 로비 참가 경로 바로 옆 설정이라 얻는 것보다 회귀 위험이 큼 |
| 전멸 승리 결과표 | 설계 불일치 | 기획 결정 반영 | 선택지를 정리해 결정을 받음 |
| LF/CRLF "혼재" | 혼재 | 두 파일 전체가 LF | 바이트 단위 재확인 |

입력 반전 항목은 이벤트 시작 조건을 다시 대조해 제외했다. 검수 결과도 **반론을 받아 다시 계산할 수 있는 근거**와 함께 제시해야 한다는 점을 확인한 사례다.

### 수정하지 않은 항목의 기준

| 기준 | 예 |
|---|---|
| 기획 결정이 필요함 | 퀘스트 실패자로 인한 이벤트 차단, NPC FakeDeath |
| 확인할 수 없는 의존이 있음 | 캐릭터 Actor Tick 끄기 (BP Event Tick 사용 여부를 소스로 알 수 없음) |
| 바꾸면 회귀 위험만 있음 | 동작에 문제없는 예측 보정, 입력 선전환 |
| 배포 단계의 값 | Steam AppID |

## 5. 반영하는 방법

### 묶음 단위 적용

수정을 한 번에 넣지 않고, **서로 의존하지 않는 묶음**으로 나눴다. 묶음마다 빌드를 확인한 뒤 다음으로 넘어갔다.

| 묶음 | 범위 | 파일 수 | 빌드 |
|---|---|---:|---|
| A | Steam 세션·로비 (잔여 세션, 검색 필터, 타임아웃) | 4 | 성공 |
| B | 네트워크 복구·화면 이동 (Travel 오탐, 로비 바인딩) | 2 | 성공 |
| C | 경기 진행 흐름 + 전멸 승리 정렬 + 상수·로그 | 7 | 성공 |
| D | 게임플레이 (드롭, 투명화, NPC 셔플, 쿨다운) | 5 | 성공 |
| E | 줄바꿈 통일 | 2 | 내용 변경 없음 |
| F | 코드 외 작업: 에디터·설정 | – | [체크리스트](02_Packaging_Checklist.md) |

| 나눈 기준 | 이유 |
|---|---|
| 시스템 경계 | 온라인 / 복구 / 경기 / 게임플레이 / 형식. 묶음 하나가 테스트 시나리오 하나에 대응한다 |
| 위험이 큰 것을 먼저 | 원래 증상과 직결된 A·B를 먼저 넣어 따로 테스트할 수 있게 했다 |
| 형식 변경 분리 | 줄바꿈 변경은 diff 전체를 바꿔 기능 변경을 가리므로 마지막에 분리했다 |

### 인코딩을 보존하는 패치 스크립트

소스는 UTF-8 BOM + CRLF다. 일반 편집 도구는 이를 깨뜨릴 수 있어서 작은 Python 스크립트로 수정했다.

1. 파일의 BOM과 줄바꿈 형식을 기억한다.
2. LF로 정규화한 뒤 "기존 문자열 → 새 문자열" 치환을 한다.
3. **치환 대상이 정확히 1번 나오지 않으면 즉시 중단한다.**
4. 원래 BOM과 줄바꿈으로 되돌려 저장한다.

3번 덕분에 "엉뚱한 곳이 바뀌는" 실수가 구조적으로 막힌다. diff에는 의도한 변경만 남는다.

### 수정 자체를 다시 검수

| 검사 | 방법 |
|---|---|
| 의도치 않은 삭제 | diff의 `-` 줄만 모아 전부 의도한 교체 대상인지 확인 |
| 구조 균형 | 파일마다 중괄호·괄호·`#pragma region/endregion`·`#if/#endif` 짝 비교 |
| 형식 | BOM·CRLF 유지, `.clang-format` 120자 제한 |
| 호출 영향 | 바뀐 함수의 모든 호출처 검색 (예: 정렬 함수에 기본값 매개변수로 기존 테스트 호환 유지) |
| 의존성 | 새로 쓴 엔진 타입의 헤더와 모듈이 `Build.cs` 범위 안인지 확인 |
| 2차 결함 | 수정이 만든 새 문제 탐색 |

이 단계에서 반영 전에 잡은 문제들이다.

| 문제 | 조치 |
|---|---|
| LOS 1차안(오브젝트 타입 트레이스)이 채널 응답을 무시해 트리거·유물이 시야를 가림 | 폐기 후 재작성 ([문서](../Debugging/Gameplay/03_Interaction_LOS_Pawn.md)) |
| 로비 잠금을 즉시 해제하는 1차안이 "불확실하면 잠금 유지"라는 기존 의도와 충돌 | 재시도 5회 후 해제로 보정 ([문서](../Refactoring/02_Lobby_StartLock.md)) |
| 세션 정리 후 화면의 방 목록이 낡은 상태로 남음 | 정리 시 목록도 비움 ([문서](../Debugging/Network/02_Steam_Stale_Session.md)) |
| 로컬 PlayerState 복제 전에 자신을 원격 화자로 착각 | 근접 음성 갱신에 가드 추가 |
| `TMap::FindOrAdd`에 원시 포인터를 넘길 때의 암시적 변환 | `TWeakObjectPtr`로 명시적 생성 |

## 6. 정리

- 정적 검수의 가치는 버그 목록보다 **각 판단에 근거와 확신 수준을 붙이는 것**에 있다.
- 코드만으로는 못 찾는 문제가 있다. 설계서 대조와 다른 관점의 교차 검증이 그 빈틈을 메운다.
- 실제로 겪은 **증상에서 출발해 원인 경로를 펼치면**, 기능별로 읽을 때보다 실제로 중요한 결함을 먼저 찾는다.
- 수정도 검수 대상이다. 작게 나누고 묶음마다 빌드로 확인하면, 문제가 생겨도 원인 범위가 한 묶음으로 좁혀진다.

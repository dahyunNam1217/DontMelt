# Don't Melt — UE5 C++ 전체 게임 아키텍처 설계서

> \*\*프로젝트:\*\* Don't Melt  
> \*\*엔진:\*\* Unreal Engine 5 / C++ 중심  
> \*\*네트워크:\*\* 2\~4인 Listen Server 기반 온라인 멀티플레이  
> \*\*출시 목표:\*\* Steam  
> \*\*포트폴리오 목표:\*\* Unreal Client Programmer  
> \*\*설계 기준:\*\* 중복 기능 최소화 · 단일 데이터 원본 · 서버 권한 · 데이터 기반 · 성능 · 유지보수 · 확장성

# 0\. 문서 목적

이 문서는 Don't Melt의 **전체 게임 아키텍처를 구현 전에 고정하기 위한 기준 문서**다.

구현 단계에서 클래스·컴포넌트·Enum·Struct·변수·RPC를 추가하기 전에 반드시 이 문서의 책임과 데이터 소유권을 먼저 확인한다.

이 문서의 목적은 다음과 같다.

* 같은 기능을 여러 클래스가 중복 구현하지 않게 한다.
* 하나의 게임 데이터에 권위 원본이 둘 이상 생기지 않게 한다.
* GameMode / GameState / PlayerState / Character의 책임을 명확히 분리한다.
* 서버 전용 정보와 클라이언트 공개 정보를 분리한다.
* 숨겨진 게임 정보를 UI에서만 가리는 것이 아니라 네트워크 레벨에서 불필요하게 전송하지 않는다.
* Tick, Replication, 물리, AI 비용을 초기 구조부터 통제한다.
* 스킬·NPC·맵·퀘스트·이벤트 추가 시 기존 핵심 클래스를 반복 수정하지 않도록 한다.
* Steam 출시와 포트폴리오 코드 리뷰를 고려해 구조적 의도를 명확히 남긴다.

이 문서는 **구현 코드를 포함하지 않는다.**

# 0.1 프로젝트 핵심 규칙

아키텍처는 다음 기획 규칙을 전제로 한다.

* 플레이어 2\~4명.
* Listen Server 기반 서버 권한형 멀티플레이.
* NPC 수는 매치 시작 플레이어 수 × NPC 배율이며 기본 최대 규모는 40명 수준을 검증 대상으로 한다.
* 플레이어와 NPC는 동일한 젤리 인간 외형을 사용한다.
* 플레이어 이름·외곽선·상대 진영·상대 유물 소지 여부 등 정체를 직접 노출하는 정보를 인게임에서 표시하지 않는다.
* 전투는 HP가 없는 판정형 원킬 구조다.
* 한 번의 공격은 공격 범위 안의 **모든 유효 대상**을 처리한다.
* 월드 장애물 뒤 대상은 공격하지 않는다.
* 동시 공격은 서버에서 먼저 유효 처리된 요청을 우선한다.
* 유물 승리와 순위 판정은 진영 상자에 등록 완료된 `RegisteredRelicCount`만 사용한다.
* 유물 운반 여부와 등록 유물 수는 서로 다른 데이터다.
* 평상시 진영별 등록 유물 수와 선두 플레이어 정보는 숨겨진 서버 정보다.
* 사망 후 30초 관전·리스폰 흐름을 사용한다.
* 스킬 쿨다운은 사망·스턴·관전 중에도 진행한다.
* 랜덤 이벤트와 퀘스트는 중첩하지 않는다.
* 중도 참가·매치 재접속·호스트 이전은 초기 범위에서 지원하지 않는다.
* 매치 판정은 항상 서버가 확정한다.

# 0.2 최종 설계 원칙

1. **Single Source of Truth** — 하나의 데이터에 권위 원본은 하나만 존재한다.
2. **Server Authority** — 공격·사망·유물·스킬 대상·퀘스트 순위·승패는 서버만 확정한다.
3. **No Premature Abstraction** — 현재 필요한 클래스와 컴포넌트만 만든다.
4. **Composition First** — 독립 책임·수명·재사용성이 있는 기능만 Component로 분리한다.
5. **Data Driven** — 밸런스 수치와 반복 콘텐츠를 코드와 분리한다.
6. **Hidden Information by Network Design** — 숨겨야 하는 정보는 일반 Replication 대상으로 두지 않는다.
7. **Event Driven** — 매 프레임 확인할 이유가 없는 기능은 Timer·Delegate·RepNotify·Notify를 사용한다.
8. **Minimal Replication** — 상태 원본만 복제하고 계산 가능한 값과 서버 내부 데이터는 복제하지 않는다.
9. **Gameplay Framework Responsibility** — GameMode는 결정, GameState는 공개, PlayerState는 플레이어 지속 상태, Controller는 소유 클라이언트 입력·표현을 담당한다.
10. **Measure Before Advanced Systems** — GAS·Mass·ReplicationGraph·Object Pool 등은 실제 병목이나 확장 요구가 확인된 뒤 도입한다.

# 2\. 시스템 간 의존 관계

## 2.1 허용 방향

```text
Widget
  → Frontend/Lobby/Match PlayerController
  → 소유 Character 또는 MatchPlayerState Component
  → MatchGameMode/RelicManager의 좁은 명령 API
  → MatchGameState의 공개 복제

Rule Data / DataTable
  → GameMode, Component, Director가 읽음

MatchGameMode
  → RelicManager, QuestDirector, EventDirector, NPCDirector
  → MatchGameState에 공개 결과 기록
```

## 2.2 금지 방향

* Widget → GameMode 직접 접근
* GameState → 승리·사망·유물 판정
* Relic → Match 종료 직접 호출
* NPCCharacter → PlayerController 직접 참조
* PlayerCharacter → RegisteredRelicCount 저장
* SkillComponent → UI Widget 직접 참조
* Data Asset → 런타임 Actor 참조
* Director 상호 간 양방향 참조

# 11\. Enum 대신 bool 또는 Gameplay Tag가 나은 항목

## 11.1 Bool

독립적이고 동시에 존재할 수 있으며 값이 두 개인 경우만 사용한다.

* `bPoseLocked`
* `bResultLocked`
* `bLobbyReady`
* `bLobbyHost`
* `bPushToTalk`
* `bTravelCommitted`

계산 가능한 `bIsAlive`, `bIsOvertime`, `bEventActive`, `bDefenseWindowActive`는 저장하지 않는다.

## 11.2 Gameplay Tag

확장 가능한 콘텐츠 ID 또는 동시에 중첩 가능한 효과에만 사용한다.

```text
Status.Stunned
Status.Invisible
Status.SpawnProtected
Status.InputReversed
Status.VisionDistorted

Skill.Invisibility
Skill.FootstepAmplify
Skill.VisionDistort

Quest.JumpCount
Quest.SprintDuration
Quest.EmoteDuration
Quest.PoseHold

QuestEvent.Jump
QuestEvent.Sprint.Start
QuestEvent.Sprint.End
QuestEvent.Emote.Start
QuestEvent.Emote.End
QuestEvent.Pose.Start
QuestEvent.Pose.End

RandomEvent.Blackout
RandomEvent.Panic
RandomEvent.Infection
```

`Action.Attack`, `Permission.Attack`, `Status.Alive`, `Status.CarryingRelic`은 만들지 않는다.

> 발소리 증폭은 대상의 범용 Status Tag로 저장하지 않는다. SkillComponent가 caster-target 효과 컨텍스트를 소유하고, 대상 경고와 caster 전용 오디오는 targeted 전달로 처리한다.

## C.5 데이터 소유권 규칙

1. 같은 게임 규칙 데이터에는 권위 원본을 하나만 둔다.
2. 복제값과 UI 캐시는 원본이 아니라 projection임을 이름과 주석으로 명확히 한다.
3. Character는 Pawn 수명 데이터만 가진다.
4. MatchPlayerState는 connection 수명 데이터만 가진다.
5. GameState는 모든 client에게 공개해도 되는 데이터만 가진다.
6. RelicManager는 유물 상태를 직접 복사해 저장하지 않고 Relic을 단일 Commit API로 변경한다.
7. RegisteredRelicCount는 최대 5개 Relic을 조회해 계산한다.
8. UI는 상태를 확정하거나 ServerTime을 수정하지 않는다.
9. SettingsSubsystem만 영구 설정을 저장한다.

## C.6 네트워크 권한 규칙

1. Client는 입력 의도만 전송한다.
2. Server RPC는 ownership, phase, LifeState, action availability, cooldown, target, distance, LOS, request id를 검증한다.
3. 공격·방어·사망·유물·스킬 대상·퀘스트 순위·승패는 서버만 확정한다.
4. LifeState/BaseSlot/Skill/Quest/Carry UI는 OwnerOnly 또는 targeted response를 우선한다.
5. 평상시 RegisteredRelicCount, carrier pointer, leading player는 전송하지 않는다.
6. Relic WorldState는 서버 전용이며, client에는 필요한 월드 표현만 relevancy 기반으로 전달한다.
7. 3초 위치 공개와 Overtime count는 제한 시간 동안만 GameState payload를 채우고 종료 즉시 비운다.
8. 반복 시간 값은 EndServerTime 기반으로 동기화한다.
9. Reliable RPC는 저빈도 핵심 요청과 개인 응답에만 사용한다.
10. 한 번 Finished/Aborted된 Match는 추가 요청과 결과 판정을 거부한다.

# 3부. 구현 기준 선언

본 문서가 승인되면 이후 구현 단계에서는 **이 문서의 클래스명, 데이터 단일 원본, 복제 범위, 생성 시점 정책을 변경하지 않는 것**을 기본 원칙으로 한다.

기능 추가로 구조 변경이 필요할 경우 다음 순서로 검토한다.

1. 기존 클래스 책임으로 처리 가능한가.
2. 기존 Component의 응집도를 해치지 않는가.
3. 새 상태가 기존 Enum/Tag/bool과 중복되는가.
4. 원본 소유자가 둘이 되지 않는가.
5. Client에 추가 데이터 전송이 정말 필요한가.
6. 프로파일 결과 없이 최적화용 구조를 미리 만들고 있지 않은가.

# 부록. 구현 단계 사용 규칙

이후 각 구현 단계에서는 반드시 다음 순서로 이 문서를 다시 확인한다.

1. 구현하려는 기능의 **현재 원본 소유자**를 확인한다.
2. 기존 클래스·컴포넌트로 처리할 수 있는지 확인한다.
3. 같은 상태를 다른 bool·Enum·Gameplay Tag로 다시 저장하지 않는지 확인한다.
4. 새 Replicated 변수가 정말 다른 연결에 필요한 데이터인지 확인한다.
5. Client가 서버 판정을 중복 수행하지 않는지 확인한다.
6. UI가 원본 데이터를 복사해 장기 보관하지 않는지 확인한다.
7. Tick을 추가하기 전에 Timer·Delegate·Notify·RepNotify로 대체 가능한지 확인한다.
8. 새 클래스를 생성하기 전에 해당 기능이 한 클래스에서만 사용되는지 확인한다.
9. 기능 구현 후 이 문서의 단일 원본 표와 실제 코드가 일치하는지 검수한다.
10. 아키텍처 변경이 필요한 경우 구현 코드만 수정하지 말고 이 문서를 먼저 갱신한다.

## 변경 관리 원칙

* 단순 밸런스 변경은 Data Asset/DataTable 수정으로 처리하고 아키텍처 버전을 올리지 않는다.
* 새로운 시스템·데이터 소유권 변경·네트워크 공개 범위 변경은 아키텍처 변경으로 취급한다.
* 임시 디버깅용 중복 상태를 추가했더라도 최종 코드에는 남기지 않는다.
* 성능 최적화 구조는 프로파일 결과를 근거로 추가한다.
* 기획서와 이 문서가 충돌하면 임의로 구현하지 않고 충돌 항목을 먼저 확정한다.

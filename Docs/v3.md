# Don't Melt — UE5 C++ 0단계 아키텍처 고정안 v3

> 범위: 2\~4인 Listen Server 기반 Steam 온라인 멀티플레이, NPC 최대 40명, 원킬 근접 전투, 유물 쟁탈, 퀘스트, 랜덤 이벤트, 관전, 리스폰, 근접 음성.
>
> 이 문서는 \*\*설계만 확정한다. 구현 코드와 Blueprint 노드는 포함하지 않는다.\*\*
>
> v3는 기존 v2의 방향을 유지하되 로비/매치 PlayerState 분리, 유물 상태 중복 제거, 숨겨진 정보 복제 축소, 설정 소유권 정리, 불필요한 FastArray·PrimaryDataAsset·RPC 제거를 추가 반영한다.

# 0\. 최종 판정

## 0.1 아키텍처 확정 여부

현재 기획 규칙을 구현하기 위한 클래스 책임, 데이터 소유권, 네트워크 권한, 확장 지점은 본 문서 기준으로 **확정 가능**하다.

다만 아래 항목은 클래스 구조가 아니라 기술 선택·밸런스 값이므로 구현 단계 전에 별도 확정한다.

* 목표 Unreal Engine 5 세부 버전
* Steam 세션/네트워크 플러그인과 음성 백엔드
* NPC 의사결정 자산: StateTree 또는 Behavior Tree
* NPC 군중 회피: Detour Crowd 또는 CharacterMovement RVO 중 하나
* 전투 Collision Channel과 방어 각도
* 물리 품질 단계와 NPC 배율 상한
* 결과 화면에서 닉네임을 다시 공개할지 여부

## 0.2 v2에서 추가 수정한 핵심 항목

|항목|v2 문제|v3 확정안|
|-|-|-|
|로비/매치 PlayerState|하나의 `ADMPlayerState`가 로비와 매치 책임을 함께 가질 가능성|`ADMLobbyPlayerState`, `ADMMatchPlayerState`로 분리|
|로비 준비 상태|GameMode Map과 GameState PlayerEntries에 중복될 가능성|준비/방장 상태는 LobbyPlayerState 단일 원본, LobbyGameState는 설정만 소유|
|유물 상태|Relic, Manager Record, Count Cache에 상태가 중복될 가능성|개별 상태는 `ADMRelic`, 운반 관계·예약은 `ADMRelicManager`; 등록 수는 최대 5개 Relic에서 즉시 계산|
|유물 복제|전체 WorldState 복제로 등록·운반 상태가 노출될 가능성|권위 `WorldState`는 서버 전용, 클라이언트에는 월드에 실제로 보이는 표현만 전달|
|유물 공개 데이터|공개 위치와 WorldState를 함께 전송|3초 공개는 식별용 ID와 위치만 전송|
|음성 설정|VoiceSubsystem과 SettingsSubsystem이 저장 책임을 함께 가짐|영구 저장은 LocalSettingsSubsystem, VoiceSubsystem은 적용된 런타임 상태만 소유|
|LifeState 공개|모든 클라이언트에 PlayerState LifeState 복제|서버와 소유 클라이언트만 사용; 타인의 사망 표현은 Character 이벤트로 처리|
|관전 단계|관전 단계와 살인자 참조를 복제 상태로 유지|최초 Client RPC의 관전 컨텍스트와 로컬 타이머로 표현; 실제 리스폰은 서버 타이머|
|리스폰 RPC|클라이언트가 리스폰을 요청|고정 30초이므로 GameMode가 자동 리스폰, 요청 RPC 제거|
|Gameplay Tag|`Permission.\*`까지 Tag로 사용|닫힌 행동 요청은 `EDMActionRequest`, Tag는 상태·콘텐츠 ID·퀘스트 이벤트에 한정|
|Data Asset|모든 정의를 `UPrimaryDataAsset`로 설계|Asset Manager가 필요하지 않은 초기 범위는 `UDataAsset`; Primary Asset은 실제 비동기 번들 요구 시만 전환|
|스킬 쿨다운|스킬 3개에 FastArray|단순 owner-only 배열과 RepNotify 사용|
|AI 부모 클래스|특정 Crowd Controller 클래스에 조기 고정|`AAIController` 기반 확정, 군중 회피 방식은 40 NPC 스파이크 후 선택|
|모듈|온라인 모듈을 초기부터 물리 분리|1차는 `DontMelt` 단일 모듈, Steam 단계에서 `DontMeltOnline` 분리|

# Part A. 0단계 수행 보고

## 1\. 이번 단계의 목표

* 전체 기능을 시스템으로 분해한다.
* GameMode/GameState, PlayerState/Character, Component 간 책임 중복을 제거한다.
* 하나의 데이터에 하나의 권위 원본만 지정한다.
* 서버 전용, 전체 복제, OwnerOnly, 로컬 표시 데이터를 분리한다.
* 구현 전에 필요한 클래스와 아직 만들지 않을 클래스를 고정한다.

## 2\. 이번 단계에서 설계하는 범위

* Gameplay Framework
* 클래스와 상속 구조
* Actor Component
* 데이터 원본과 복제 범위
* Enum, Gameplay Tag, Struct
* DataTable/Data Asset/Config/SaveGame
* RPC, RepNotify, Delegate, Timer 흐름
* 폴더/모듈 구조
* 구현 순서와 테스트 경계

## 3\. 이번 단계에서 구현하지 않는 범위

* C++ 코드 생성
* Blueprint 노드 구성
* Steam 플러그인 설정
* 세션·음성 실제 연결
* StateTree/Behavior Tree 자산 제작
* Collision Channel 실제 생성
* 애니메이션 Notify 배치
* UI 디자인과 위젯 제작
* 구체적인 밸런스 값 확정

## 4\. 기존 구조와의 사전 중복 검사 결과

|검사 항목|판정|최종 처리|

## 8\. 네트워크 권한 구조

* Listen Server가 모든 게임 규칙의 최종 권한을 가진다.
* Client는 입력 의도와 상호작용 요청만 보낸다.
* 공격 적중, 사망, 유물 상태, 스킬 대상, 퀘스트 순위, 승패는 서버만 확정한다.
* 비공개 데이터는 UI에서 숨기는 데 그치지 않고 일반 복제 대상에서 제외한다.
* UI는 RepNotify/Delegate/Targeted Client RPC의 결과만 표시한다.

## 9\. 구현 순서

1. Core type, rule data, Lobby/Match Framework
2. Player/NPC 공통 Character와 기본 이동
3. Relic 수직 슬라이스
4. Combat, Death, Respawn
5. Pose
6. NPC AI와 40명 성능 검증
7. Quest
8. Skill
9. Spectator/Overtime
10. Random Event
11. Steam Session/Voice
12. UI/Audio/VFX/최적화

## 10\. 코드 또는 구현 방법

이번 단계에서는 코드 대신 아래 계약만 확정한다.

* 외부 입력 함수: `Request...`
* 서버 내부 상태 확정: `Commit...`, `Apply...`, `Transition...`
* 공통 행동 검사: `CanPerformAction(EDMActionRequest)`
* 중앙 경기 판정: `EvaluateMatchResult`
* 유물 변경: RelicManager의 단일 Commit API만 사용
* UI 변경: RepNotify → Native Delegate → Widget 갱신

* 동일 유물 예약 경쟁

## 13\. 예상 실패 사례

* Manager와 Actor가 같은 유물 상태를 각각 변경
* GameState가 승리 조건을 직접 계산
* UI가 쿨다운을 자체 감소시켜 서버와 불일치
* Relic WorldState를 전체 복제해 숨겨진 정보 유출
* Lobby GameMode와 LobbyPlayerState가 준비 상태를 이중 저장
* 사망 시 Character는 파괴됐지만 Skill cooldown도 초기화
* Player/NPC 물리 품질을 동일하게 유지해 CPU 과부하

## 14\. 성능 점검

* 모든 커스텀 Tick 기본 비활성

# 7\. 컴포넌트로 만들면 안 되는 기능

* `HealthComponent`: HP 없음.
* `InventoryComponent`: 유물 1개 외 일반 슬롯 없음.
* `RelicCarrierComponent`: Manager carrier index와 중복.
* `MovementStateComponent`: CharacterMovement에서 계산 가능.
* `CooldownComponent`: Combat/Skill이 각자 소유.
* `TargetingComponent`: Skill 대상 정책만 존재.
* `DeathComponent`: LifeState는 MatchPlayerState, 표현은 Physics.
* `AnimationComponent`: AnimInstance/Montage/Notify 사용.
* `RespawnComponent`: GameMode의 서버 생명주기.
* `VoiceComponent`: 참가자/채널은 앱 수명 Subsystem.
* `MatchManager`: MatchGameMode와 중복.

## C.5 데이터 소유권 규칙

1. 같은 게임 규칙 데이터에는 권위 원본을 하나만 둔다.
2. 복제값과 UI 캐시는 원본이 아니라 projection임을 이름과 주석으로 명확히 한다.
3. Character는 Pawn 수명 데이터만 가진다.
4. MatchPlayerState는 connection 수명 데이터만 가진다.
5. GameState는 모든 client에게 공개해도 되는 데이터만 가진다.
6. RelicManager는 유물 상태를 직접 복사해 저장하지 않고 Relic을 단일 Commit API로 변경한다.
7. RegisteredRelicCount는 최대 5개 Relic을 조회해 계산한다.
8. UI는 상태를 확정하거나 ServerTime을 수정하지 않는다.
9. SettingsSubsystem만 영구 설정을 저장한다.

## C.6 네트워크 권한 규칙

1. Client는 입력 의도만 전송한다.
2. Server RPC는 ownership, phase, LifeState, action availability, cooldown, target, distance, LOS, request id를 검증한다.
3. 공격·방어·사망·유물·스킬 대상·퀘스트 순위·승패는 서버만 확정한다.
4. LifeState/BaseSlot/Skill/Quest/Carry UI는 OwnerOnly 또는 targeted response를 우선한다.
5. 평상시 RegisteredRelicCount, carrier pointer, leading player는 전송하지 않는다.
6. Relic WorldState는 서버 전용이며, client에는 필요한 월드 표현만 relevancy 기반으로 전달한다.
7. 3초 위치 공개와 Overtime count는 제한 시간 동안만 GameState payload를 채우고 종료 즉시 비운다.
8. 반복 시간 값은 EndServerTime 기반으로 동기화한다.
9. Reliable RPC는 저빈도 핵심 요청과 개인 응답에만 사용한다.
10. 한 번 Finished/Aborted된 Match는 추가 요청과 결과 판정을 거부한다.

# 최종 승인 문구

본 문서가 승인되면 이후 구현 단계에서는 **이 문서의 클래스명, 데이터 단일 원본, 복제 범위, 생성 시점 정책을 변경하지 않는 것**을 기본 원칙으로 한다.

기능 추가로 구조 변경이 필요할 경우 다음 순서로 검토한다.

1. 기존 클래스 책임으로 처리 가능한가.
2. 기존 Component의 응집도를 해치지 않는가.
3. 새 상태가 기존 Enum/Tag/bool과 중복되는가.
4. 원본 소유자가 둘이 되지 않는가.
5. Client에 추가 데이터 전송이 정말 필요한가.
6. 프로파일 결과 없이 최적화용 구조를 미리 만들고 있지 않은가.

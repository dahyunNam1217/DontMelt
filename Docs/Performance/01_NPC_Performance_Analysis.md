# NPC가 프레임 저하의 원인인지 판단한 과정

| 항목 | 내용 |
|---|---|
| 질문 | 4인 경기에서 NPC가 수십 명일 때 프레임이 떨어진다. AI를 먼저 최적화해야 하는가 |
| 접근 | 측정 값으로 AI와 CharacterMovement를 분리해 보고, 정적 검색으로 게임 코드 쪽 낭비부터 확인했다 |
| 결론 | 측정 값만으로는 AI가 주원인이라고 볼 수 없었다. 후보는 엔진 기본값으로 동작하는 복제·애니메이션·이동이고, 흔한 애니메이션 최적화 하나는 게임 규칙과 충돌해 쓰지 않기로 했다 |

## 측정으로 본 것

6단계에서 NPC를 플레이어당 10명씩(4인 기준 40명) 생성하도록 만든 뒤, 한 프로세스 PIE에서 프레임이 크게 떨어지는 구간이 있었다. NPC 수만 보고 AI부터 손대기 전에 시간이 어디에 쓰이는지 측정했다.

| 항목 | 측정값 |
|---|---|
| AI 평균 비용 | 약 0.12~0.25ms |
| AI 최대 비용 | 약 0.9~1.31ms |
| MoveTo 최대 비용 | 약 1.39ms |
| CharacterMovement | 단일 PIE 프로세스 약 14~17ms, 클라이언트 분리 측정 약 4.05~5.51ms |

- AI 비용은 평균·최대 모두 프레임 예산에 비해 작았다.
- CharacterMovement는 **실행 방식에 따라 3배 이상** 차이가 났다. 단일 PIE 프로세스는 서버와 여러 클라이언트의 이동을 한 프로세스에서 모두 처리하므로, 이 숫자를 실제 플레이 비용으로 볼 수 없었다.

그래서 행동 전환 시간을 줄이거나 AI를 다시 짜는 대신 설정을 유지했다. 평균만 보지 않고 최대값과 실행 환경 차이를 함께 기록했다.

## 정적 검색으로 본 것

측정 다음에는 코드 쪽에서 이미 잘 되어 있는 부분부터 확인해, 효과 없는 최적화를 걸러 냈다.

| 항목 | 결과 |
|---|---|
| 직접 구현한 Actor `Tick()` / `TickComponent()` / 위젯 `NativeTick()` | 0개 |
| 컴포넌트·관리자의 `bCanEverTick` | 모두 false |
| AI | 타이머와 이동 완료 이벤트 기반 상태 머신 |
| `GetAllActorsOfClass` | 사용 없음. `TActorIterator`는 초기화와 캐시 갱신에만 사용 |
| UI 갱신 | 0.05~0.25초 로컬 타이머, 표시 중일 때만 동작 |
| 상호작용 시야 재검사 | 진행 중인 상호작용에만 0.1초 주기 |
| 젤리 애니메이션 `NativeUpdateAnimation` | 할당 없는 계산 (스프링 7개, 프레임당 최대 12 서브스텝) |

게임 코드 차원의 대량 Tick 낭비는 없었다. 남은 후보는 **엔진 기본값으로 동작하는 부분**이다. 별도 AI 프레임워크(Mass, StateTree)나 Object Pool을 도입할 근거도 없었다.

## 병목 후보

| 대상 | 현재 | 비용 원인 | 개선 후보 | 확인할 점 |
|---|---|---|---|---|
| NPC 복제 | NPC 전용 설정 없음 (Pawn 기본 NetUpdateFrequency 100) | 서버가 NPC 전체를 높은 빈도로 복제 검토, 이동 대역폭 | NPC만 `SetNetUpdateFrequency(30)`, `SetMinNetUpdateFrequency(10)` | 클라이언트에서 NPC 이동이 끊기는지 |
| NPC 애니메이션 (호스트) | 메시 기본값 AlwaysTickPose | Listen 호스트가 화면 밖 NPC까지 포즈 갱신 | NPC만 Update Rate Optimization(URO) | 먼 NPC의 발소리 타이밍 |
| NPC 이동 | CharacterMovement Walking | 서버에서 NPC 전체의 바닥 판정 | NPC만 NavWalking | 플레이어와의 충돌 차이 |
| 군집 발소리 | NPC마다 원샷 재생 | 군집 이동 시 동시 재생 수 급증 | 사운드 에셋 Concurrency (예: 최대 8개, 먼 것부터 정지) | 코드 변경 없음 |
| 캐릭터 Actor Tick | 기본 활성 | 빈 Tick 디스패치 | 오버라이드가 없으므로 비활성화 가능 | BP Event Tick 사용 여부를 먼저 확인해야 해 보류 |

## 최적화가 게임 규칙을 깨는 경우

애니메이션 비용을 줄이는 가장 흔한 설정은 `VisibilityBasedAnimTickOption = OnlyTickPoseWhenRendered`(화면에 보일 때만 포즈 갱신)다. 이 프로젝트에서는 **쓰지 않기로 했다.**

- 발소리는 애니메이션 노티파이(`UDMAnimNotify_Footstep`)로 재생된다.
- 화면 밖 NPC의 포즈 갱신이 멈추면 **노티파이도 발생하지 않아 발소리가 사라진다.**
- 이 게임에서 발소리는 "등 뒤에서 누가 다가오는가"를 판단하는 **게임플레이 단서**다. 발소리 증폭 스킬도 이 소리에 의존한다.
- 플레이어 캐릭터가 `AlwaysTickPoseAndRefreshBones`를 쓰는 것도 같은 이유다. 투명 상태에서도 발소리 노티파이가 나와야 한다.

대안은 **갱신 빈도만 낮추고 노티파이는 유지하는 URO**다. 적용할 때도 먼 거리 NPC의 발소리 타이밍이 어긋나지 않는지 함께 확인한다.

## NPC 수 변경

이후 NPC 배율을 10에서 15로 올려, 4인 기준 최대 60명이 됐다(`DefaultNPCMultiplier = 15`, Director 허용 범위 1~60). 위 측정은 40명 기준이므로, 최대 부하 측정은 60명으로 다시 한다. 측정 구성과 진행 원칙은 [프로파일링 계획](03_Profiling_Plan.md)에 정리했다.

## 정리

- 성능 문제를 **측정 없이 단정하지 않는다.** 평균과 최대, 실행 환경 차이를 함께 본다.
- 최적화 후보를 고르기 전에 이미 잘 되어 있는 부분을 확인해 효과 없는 작업을 걸러 낸다.
- 일반적인 최적화 설정도 **게임 규칙과 충돌할 수 있다.** 성능 설정을 바꿀 때는 그 시스템에 의존하는 게임플레이를 같이 따진다.

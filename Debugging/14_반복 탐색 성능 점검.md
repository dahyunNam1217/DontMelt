# 불필요한 반복문 / 반복 탐색 성능 점검

> **기록 유형:** 성능 점검 / Query 구조 검토

## 1. 점검 대상

기능 구현 후 다음 패턴이 자주 실행되는 경로에 남아 있는지 확인한다.

```text
불필요한 for loop
중첩 반복문
매번 Actor 전체 검색
같은 배열 반복 순회
같은 계산 반복
```

## 2. 특히 확인하는 API

예:

```cpp
UGameplayStatics::GetAllActorsOfClass(
    GetWorld(),
    TargetClass,
    Actors
);
```

Epic 공식 문서에서도 지정 Class Actor가 많으면 느릴 수 있는 Operation으로 설명한다.

따라서:

```text
초기화 시 1회
```

와:

```text
Tick마다 전체 검색
```

을 같은 비용 구조로 보지 않는다.

## 3. 성능 판단 기준

반복문이 존재한다는 사실만으로 제거하지 않는다.

```text
실제 비용
≈
호출 빈도
×
순회 대상 크기
×
Loop 내부 작업 비용
```

예:

```text
10개 Actor를 Match 시작 시 한 번 검색
→ 문제 아닐 가능성이 큼

1000개 Actor를 Tick마다 검색
→ 구조 재검토 필요
```

## 4. 대안

요구사항에 따라:

```text
Reference Cache
Registry
Component Reference
Event-driven Update
Actor Spawn/Destroy 시 목록 갱신
여러 순회 병합
TSet/TMap 기반 Lookup
```

을 검토한다.

## 5. 캐싱도 무조건 정답은 아니다

Cache를 만들면 다음 비용이 생긴다.

```text
Lifetime 관리
삭제된 Actor 처리
Registry Sync
Memory
Stale Reference 가능성
```

따라서 검색 횟수가 적다면 단순 Query가 더 유지보수하기 쉬울 수 있다.

## 6. 디버깅/프로파일링 순서

```text
1. 해당 함수 호출 빈도 확인
2. 대상 Actor/Array 크기 확인
3. Loop 내부 작업 확인
4. 실제 Frame/Profile 비용 확인
5. Bottleneck일 때 구조 변경
```

## 7. 기록 결론

반복문을 코드 스타일 문제로 제거하지 않고 **빈도 × 데이터 크기 × 작업 비용을 근거로 탐색 구조를 판단**하는 성능 점검 기준을 정리했다.

## 관련 개념

`GetAllActorsOfClass` `TArray` `Registry` `Caching` `Profiling`
